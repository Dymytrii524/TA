# Trans-Atlas PR #21: рішення щодо quarantine та subset accounting

Дата: 29.09.2026. Статус ADR-R21-02: **ACCEPTED, варіант B погоджений власником продукту о 22:10 EEST**. Підстава: наданий користувачем знімок із погодженням B та withdraw-all для змішаного гаманця, дорученням зафіксувати ADR і реалізувати R21-01/02/03 окремими комітами. Реалізацію та commit/push у PR дозволено цим окремим дорученням; технічне приймання, merge, deployment і реальні кошти не дозволені автоматично.

## Висновок для власника продукту

Рекомендую **B: повний перевірений облік контракту + окремий TA-підоблік + quarantine бізнес-прив’язки**. Стороння угода не повинна зупиняти TA лише через відсутність локального запису, але її суми не можна виключати з реальної агрегованої виплати. Це зберігає погоджений F05-B: withdraw усього балансу гаманця та доказове внутрішнє рознесення тільки підтверджених TA-нарахувань.

Пропонований B не означає, що TA визнає зовнішню угоду своїм замовленням, проводить її KYB або гарантує її економічну чи юридичну правомірність. Quarantine тут означає відсутність підтвердженої бізнес-прив’язки, а не блокування токенів.

## Перевірена база і межі

Поточний [PR #21](https://github.com/Dymytrii524/TA/pull/21) повторно перевірено лише щодо стану: OPEN, HEAD `bad53cc9c2248950339738af9c8af6fb5a8e3c3d`, без auto-merge; усі 12 checks SUCCESS. Нового тестового прогону в цьому документальному завданні немає; відтворення R21-01/02/03 успадковані з попереднього рев’ю, а не видані за тести виправлення.

Контракт допускає `create()` без реєстрації угоди в TA, а `withdraw()` виводить повний `claimable[msg.sender]` без ID угоди ([Solidity](https://github.com/Dymytrii524/TA/blob/bad53cc9c2248950339738af9c8af6fb5a8e3c3d/web3-sprint-0/src/TransAtlasEscrow.sol)). Водночас воркер читає глобальну історію `Settled`/`Withdrawn`, вимагає frozen terms для кожного settlement і звіряє загальні суми, тому відсутність одного локального запису зупиняє весь reconciliation ([wallet runtime](https://github.com/Dymytrii524/TA/blob/bad53cc9c2248950339738af9c8af6fb5a8e3c3d/web3-sprint-0/runtime/wallet.mjs)).

У попередньому локальному відтворенні стороння угода на 1 atomic заблокувала HTTP-читання іншого авторизованого wallet; прямий on-chain withdraw цього wallet спрацював. Це доказ дефекту доступності API/обліку, не крадіжки коштів; лог і сценарій збережені поряд зі звітом у `evidence/`.

## ADR-R21-02: рекомендоване рішення B

### Розділити походження й достовірність

Запровадити дві незалежні ознаки. Бізнес-класифікація не повинна підміняти перевірку канонічності блокчейну.

| Ознака | Значення | Правило |
|---|---|---|
| Chain integrity | `VERIFIED` | Перевірено chain/contract/token/code, receipt, log, канонічний блок та finality |
| Chain integrity | `UNVERIFIED` / `CONFLICT` | Недостатньо доказів або є суперечність; жодного фінального lot/paid |
| Business provenance | `TA_MATCHED` | Повний scoped escrow ID зіставлено з чинним immutable TA frozen snapshot; поля та hash збігаються |
| Business provenance | `UNATTRIBUTED` | Немає доведеної TA-прив’язки; перевірені chain facts зберігаються в окремому підобліку |
| Business provenance | `TA_MISMATCH` | TA-запис існує, але не збігається з chain facts; це інцидент, не спосіб перекласти запис у «зовнішні» |

Лише комбінація `VERIFIED + UNATTRIBUTED` є штатним quarantine без глобального блокування. Наявність адреси у wallet bindings, однаковий payer, nonce, agreement hash або поява довільного локального deal не надає автоматично статусу `TA_MATCHED`.

### Повний облік контракту

- **Scope:** кожен запис належить до `(chain_id, escrow_contract, token)`; lot додатково має beneficiary wallet. Мережі, контракти, токени та різні адреси не змішуються.
- **Chain-first ingestion:** спочатку отримати й перевірити факти незалежно від TA-реєстрації. Для зовнішнього escrow потрібні канонічний `Funded`, незмінні parties/amount/termsHash із контракту на тому самому anchor та відповідний `Settled`; зафіксований hash не слід подавати як юридично перевірені умови зовнішньої угоди.
- **Повнота:** обробити всю потрібну історію від deployment або від доведено повного checkpoint. Усі потрібні блоки/діапазони мають бути прочитані без пропусків; RPC timeout чи обрізаний діапазон не перетворюється на empty success.
- **Lots:** settlement створює ненульові refund/proceeds окремо; external lot має реальний escrow ID, але `deal_id=null`. Фіктивний deal або frozen snapshot створювати заборонено.
- **Canonical order:** `(block_number, transaction_index, log_index)`, із block hash і tx hash як доказовою ідентичністю. Повтор не створює нового lot/withdrawal.
- **Unsolicited events:** підтверджений on-chain факт обліковується і без TA-intent. Відсутність або невірний API-intent не надає права викинути справжню подію.

Для MVP рекомендується зберегти повну глобальну звірку перед публікацією нового фінального snapshot. Незалежну доступність при реальному global-integrity incident цей ADR не обіцяє: його гарантія стосується валідної сторонньої угоди, а не неперевіреної або суперечливої історії.

### Інваріанти subset accounting

Усі суми є цілими atomic units, у JSON передаються десятковими рядками. Позначення `T` означає TA_MATCHED, `U` означає VERIFIED/UNATTRIBUTED; формули є новими вимогами до реалізації.

Для wallet `w` у одному scope на одному finalized anchor `H`:

```text
T_open(w,H) + U_open(w,H) = claimable(w,H)
sum_w [T_open(w,H) + U_open(w,H)] = totalClaimable(H)
sum_verified_withdrawals amount = totalWithdrawn(H)
sum_all_settlement_shares = sum_verified_withdrawals amount + totalClaimable(H)
```

Додатковий контроль повної фінансової історії: `totalDeposited = locked + totalClaimable + totalWithdrawn`, а token balance контракту має бути не меншим за `locked + totalClaimable`. Надлишковий прямий переказ токенів не створює lot і не є причиною довільно розподілити кошти між угодами.

Для кожного withdrawal `x` гаманець виводить суму всіх попередніх невиведених lots, не лише TA:

```text
withdrawal.amount = sum(TA allocation legs) + sum(unattributed allocation legs)
```

TA-підоблік не порівнюється самостійно з глобальним `totalClaimable`. Непояснений залишок не можна оформити як «external amount»: кожна зовнішня частина потребує власного перевіреного lot.

### Змішаний гаманець і правила API

Рекомендована поведінка: авторизований wallet може підготувати unsigned withdraw-all для свого повністю звіреного балансу, у тому числі коли частина або весь баланс є unattributed. Це розширення інтерпретації відповіді API потребує явного погодження разом із B; воно не реєструє зовнішній рейс у TA.

| Сценарій, суми умовні в одному token/scope | Очікуваний результат |
|---|---|
| TA A=600, TA B=400; стороння угода на 1 у іншого wallet | TA wallet лишається доступним: total=1000, TA=1000, unattributed=0 |
| TA A=600 і зовнішній lot=400 у того самого wallet | API: total=1000, TA=600, unattributed=400; withdraw 1000 розноситься 600/400 без fake deal |
| У wallet лише зовнішній lot=400 | За чинної перевіреної прив’язки й права на фінансову операцію: total=400, TA=0, unattributed=400; withdraw-all дозволений за рекомендацією B |
| TA=600, відомий external=400, але Withdrawn=1100 | Немає доказів ще на 100: новий фінальний snapshot та intent не публікуються, HTTP 503 |
| Після підготовки з'явився зовнішній lot=200 | При execution перевіряється фактичний full sweep 1200; quote не є гарантією суми |

Пропоновані поля wallet claims: `claimable_atomic` як повний on-chain total для сумісності; `ta_claimable_atomic`; `unattributed_claimable_atomic`; `reconciliation_status`; `block_number`; `block_hash`; `policy_version`; `projection_revision`; попередження `WITHDRAW_ALL_INCLUDES_UNATTRIBUTED`, якщо сума unattributed ненульова.

Пропонований текст UI: «Буде виведено весь доступний баланс гаманця на момент виконання. Частина не прив’язана до угод TA; вона не буде показана як оплата рейсу TA». `SETTLED` не стає «оплачено», а `allocation` не стає юридичним підтвердженням погашення інвойсу.

Усі методи зберігають trusted authentication, company permission, active binding, повторну перевірку revocation та idempotency. Клієнт не задає sender, recipient, суму, deal ID, класифікацію чи policy version; endpoint не підписує та не транслює транзакцію. У company API не показуються інші wallets, чужі TA deal IDs або загальний quarantine-журнал.

### Quarantine, інциденти та ізоляція помилок

Quarantine має бути append-only журналом прив’язки з причиною, proof references, першою появою та версіями рішень. Відсутність TA mapping не потребує ручного підтвердження, щоб перевірений external lot потрапив у глобальні суми.

| Ситуація | Поведінка MVP |
|---|---|
| Валідний невідомий escrow, усі chain proofs доступні | Облік як UNATTRIBUTED; quarantine business mapping; API інших і змішаних wallets працює |
| Відомий TA escrow не збігається з frozen terms | Інцидент `TA_MISMATCH`; не перекласифіковувати в external, не показувати paid; новий глобальний snapshot не публікувати |
| Не вдалося прочитати/перевірити receipt, Funded або стан unknown escrow | Це UNVERIFIED, не штатний quarantine; HTTP 503 без нових allocations |
| Wrong chain/code/token, global sum mismatch, anchor змінився | Fail closed для відповідного contract scope; не продовжувати з частковою історією |
| Post-finality breach | Зупинити нову публікацію, зберегти докази; recovery лише за окремою процедурою |

Історичний останній добрий snapshot можна зберігати для аудиту, але не повертати його як свіжий успішний `claims` після невдалої поточної звірки. За потреби окремого history endpoint його слід явно відділити від доступного зараз балансу.

### Пізнє зіставлення й історія

- **Підстава:** потрібен підтверджений immutable TA snapshot і повний збіг chain/contract/token/escrow, parties, amount та termsHash. Відновлення втраченого TA-запису потребує доказів із резервної копії або попереднього аудиту; сторонню угоду не можна «прийняти заднім числом» лише ручним створенням deal.
- **Дозвіл:** пропонується окрема привілейована процедура з аудитом і другим погодженням, без публічного endpoint. Постійне автоматичне імпортування довільних external deals не входить у B.
- **Незмінність:** chain event, lot ID і withdrawal amount не змінюються. Перенесення provenance з U до T створює нову classification/projection revision; стара версія лишається доступною для аудиту.
- **Виведений external lot:** нова TA allocation reference посилається на той самий withdrawal. Нова виплата, дубль суми або новий on-chain ефект не створюються.
- **Помилкове зіставлення:** корекція через нову revision та audit record, не UPDATE/DELETE старого фінального snapshot. До доказової корекції TA-позначка оплати не публікується.

### Схема та міграція

Цільова схема має окремо зберігати chain facts, provenance revisions, lots/allocation legs і publishable snapshots. Пропонована версія політики: `F05-B/2`; поточні immutable snapshots дозволяють лише `F05-B/1` та унікальність за block hash, тому нову ревізію не можна впровадити лише зміною JSON ([міграція 005](https://github.com/Dymytrii524/TA/blob/bad53cc9c2248950339738af9c8af6fb5a8e3c3d/web3-sprint-0/db/005_wallet_accounting.sql)).

Рекомендований міграційний шлях: нові side-by-side таблиці V2 із FK на факти та унікальністю `(scope, anchor_hash, policy_version, projection_revision)`, один атомарно перемиканий active pointer. Старі snapshots і захисні тригери лишаються незмінними; нова схема повинна забезпечувати сумісне читання старої історії, а не переписувати її.

Для порожньої БД потрібен clean install; для populated V1 потрібен явний inventory та replay/backfill у V2 на тому самому anchor, звірка сум, backup/restore rehearsal і лише тоді перемикання. Якщо доказів недостатньо, міграція зупиняється атомарно. Rollback не означає повернення до завідомо вразливого V1 API зі статусом «healthy»; допустима зупинка нових операцій зі збереженням доказів.

### Наслідки і залишкові ризики

- **Перевага:** валідний unknown escrow більше не є причиною `missing frozen deal history` для всього TA. Суми external і TA звіряються разом, але бізнес-деталізація не змішується.
- **Складність:** додаються два підобліки, versioned classifications, migration/backfill і API/UI пояснення змішаного балансу.
- **Ресурсні атаки:** B не обіцяє необмежену доступність при масовому створенні external deals. Потрібні bounded RPC batches, retry/checkpoints, lag/timeout metrics, alert deduplication; неможливість завершити перевірку повертає 503, а не пропускає події.
- **Contract capacity:** сторонні депозити можуть займати спільний `maxLiability`; B не обмежує create і не звільняє цю місткість. Цей окремий ризик прямо випливає з permissionless create і загального ліміту в [контракті](https://github.com/Dymytrii524/TA/blob/bad53cc9c2248950339738af9c8af6fb5a8e3c3d/web3-sprint-0/src/TransAtlasEscrow.sol); потребує окремого рішення для production.
- **Не закрито:** production TA auth, PostgreSQL multi-session concurrency, full deal HTTP/indexer, post-finality recovery, незалежний аудит та готовність до реальних коштів.

## Рішення, яке потрібно погодити

Погоджено ADR-R21-02/B: зберегти permissionless контракт; вести повний verified ledger і TA subset; unknown verified суми враховувати без fake deal; дозволяти авторизований withdraw-all зі змішаним або unattributed-only балансом; пізнє зіставлення робити доказово й версійно. Справжні integrity failures надалі зупиняють нову фінальну публікацію.

Погодження цього ADR закриє лише вибір архітектури. R21-02 лишається **OPEN/P1** до реалізації та виконання регресій, перелічених в оновленій матриці; R21-01 і R21-03 виправляються окремо.
