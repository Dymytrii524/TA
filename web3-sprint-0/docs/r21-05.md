# R21-05: reject malformed binding UUIDs before persistence

Both wallet HTTP paths now require the full 8-4-4-4-12 hexadecimal UUID shape,
accepting either case. Authenticated malformed paths receive stable 404
`not found`, without calling SQL, starting a transaction, querying RPC or
emitting a reconciliation-failure audit. Authentication still runs first.

`authorizeWallet` and `prepareWithdrawal` also guard their direct inputs before
any SQL or transaction with domain 422 `invalid wallet binding id`. This protects
non-HTTP callers without conflating client input with infrastructure failures.

OpenAPI BindingId documents the lexical rule and HTTP 404/403 distinction.
Well-formed unknown/foreign/revoked UUIDs still receive 403. Real DB/RPC failures
still receive sanitized 503 `RECONCILIATION_UNAVAILABLE`.

The new `tests/wallet-id.test.mjs` first reproduced `503 !== 404` against the
unpatched handler. Its fixed expectations cover 22 real HTTP malformed paths,
34 direct-helper negatives (including types and trailing newlines), zero DB/RPC activity for invalid identifiers,
healthy 200/201, authentication, case-insensitive UUIDs, and 503 failure controls.
The test runs in the existing local EVM CI job, without any deployment.
